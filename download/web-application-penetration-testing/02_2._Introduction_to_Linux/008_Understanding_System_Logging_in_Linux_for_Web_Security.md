## Introduction to logging systems[#](https://www.educative.io/courses/web-application-penetration-testing/system-logging#Introduction-to-logging-systems)

Log files help provide an audit trail of the system’s operations. These files exhibit essential information in case of a security breach or when troubleshooting a system problem. When an issue arises in the operating system, analyzing the log files is the first thing a pentester, or a system administrator, needs to do. Therefore, when securing a Linux machine, we need a proper understanding of the management of the logging function to determine if a system has a vulnerability or has been attacked and then determine what happened and who was responsible.

### The `rsyslog` logging daemon[#](https://www.educative.io/courses/web-application-penetration-testing/system-logging#The-rsyslog-logging-daemon)

The log files are plain text files in the `/var/log` directory. These logs are generated by the `Syslog` or `rsyslog` daemon in the Linux system. Several variations of these daemons are used on all the different Linux distributions. Since Ubuntu is Debian based, it comes with `rsyslog` by default.

> **Note**: Accessing log files usually requires root or administrator privileges.

Let's go through `alternatives.log` below and see what kind of information we can obtain. It contains information on various installations and updates that have taken place on the system. Feel free to look through the other log files as well.

## Linux system logs[#](https://www.educative.io/courses/web-application-penetration-testing/system-logging#Linux-system-logs)

Most of the Linux system log directories can be grouped and are located in the `var/log` subdirectory in the Linux system. These are the four categories of these files:

- System logs
- Event logs
- Application logs
- Service logs

### System logs[#](https://www.educative.io/courses/web-application-penetration-testing/system-logging#System-logs)

The system logs are critical for the functionalities of the system because they contain the most vital information. The most common log files are:

## System Log Files

|  |  |
| --- | --- |
| **Log File** | **Description** |
| `boot.log` | This contains information related to boot operations. |
| `auth.log` | This contains all the authentication logs including both successful and failed attempts. |
| `httpd` | This is for Apache access and error logs for web servers. |
| `mysqld.log` | This is the MySQL database server log file. |
| `debug` | This contains messages related to debugging the system and troubleshooting information. |
| `daemon.log` | This contains information about the running processes in the system. |
| `maillog` | This contains information related to mail servers in the web server or Linux system. |
| `kern.log` | This contains information related to the working of the kernel. |

Some log files aren’t ASCII files, which means that we won’t be able to `cat` them. One such example is `lastlog`. We can use its namesake command, `lastlog`, to view information about recent logins. Since the terminals on this platform are served fresh every time we first run them, we won’t find any meaningful information through this command when we test it.

### Enabling and disabling logging[#](https://www.educative.io/courses/web-application-penetration-testing/system-logging#Enabling-and-disabling-logging)

On earlier versions of Linux distros, when a user logged in to the system, the system event logs recorded their login time. Nowadays, this has (mostly) been replaced with the journal. Even so, it’s always a good practice, as a system administrator and pentester, to know what sort of systems we’re managing or up against and to confirm whether the logging daemon is functioning.

Traditionally, `rsyslog` gets information from `rsyslog.conf`, which is usually located in the `/etc` directory. This file provides `rsyslog` with information on where to save the log messages.

To enable the logging to take place in an older Linux system, we apply the `service` command with the following syntax:

```
service <servicename> start|stop|restart
```

Of course, that won’t work here on our terminals since we’re using the latest official Kali distribution at the time of writing. What we’ll use instead is `journalctl`.

> **Note:** For a lot more information, feel free to look into the contents of `/var/log/README`.
