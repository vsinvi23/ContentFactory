# Model and Context Trade-offs

Explore how model and context choices drive the latency and cost of agent systems at enterprise scale. Learn to apply model routing, compare long context with retrieval, use context caching effectively, and estimate cost per request for customer conversations.

We'll cover the following...

- [Context caching](https://www.educative.io/courses/forward-deployed-engineer/model-and-context-trade-offs#Context-caching)
- [Estimating cost per request](https://www.educative.io/courses/forward-deployed-engineer/model-and-context-trade-offs#Estimating-cost-per-request)
- [Common trade-off mistakes](https://www.educative.io/courses/forward-deployed-engineer/model-and-context-trade-offs#Common-trade-off-mistakes)

A design that works well in a pilot with fifty users can become too slow or too expensive when it serves fifty thousand. Most of that difference comes from two decisions: which model handles each request, and how much context is sent with it. Every token sent to or generated by a model adds cost and latency, and those small amounts multiply quickly at enterprise scale. A customer’s finance team will eventually ask what each conversation costs, and an FDE needs a clear, defensible answer.

FDE interviewers often raise these trade-offs as follow-up questions in system design rounds. They may ask how to reduce latency, whether the full document set should simply go into the context window, or what the system will cost per month. Strong answers connect each choice to the task’s quality requirements and back it with a simple estimate. This lesson covers model routing, long context versus retrieval, context caching, and cost estimation.

## Model routing[#](https://www.educative.io/courses/forward-deployed-engineer/model-and-context-trade-offs#Model-routing)

Model routing sends each request to the least expensive model that can handle it well. Most enterprise traffic is routine: classifying a request, extracting fields, or answering a common question. A smaller fraction requires deeper reasoning, such as analyzing a complex dispute or planning a multi-step resolution. Sending every request to the most capable model wastes money and adds latency, while sending every request to the fastest model sacrifices quality on the hard cases.

There are several ways to route requests. **Rule-based routing** uses known signals, such as request type or customer tier, to choose the model. **Classifier-based routing** uses a fast model to judge the request’s complexity before choosing. **Escalation routing** tries the faster model first and moves to the stronger model when confidence is low or validation fails. ## Long context versus retrieval[#](https://www.educative.io/courses/forward-deployed-engineer/model-and-context-trade-offs#Long-context-versus-retrieval)

Gemini models support very long context windows, large enough to hold entire manuals, contracts, or codebases in a single request. This raises a common question: why build retrieval at all if the whole document set fits in the context?

|  |  |  |
| --- | --- | --- |
| **Consideration** | **Long context** | **Retrieval (RAG)** |
| Setup effort | Minimal | Requires indexing and a retrieval pipeline |
| Cost per request | High, since every request sends all content | Low, since only relevant passages are sent |
| Latency | Higher with large inputs | Lower for most queries |
| Content size | Limited by the context window | Scales to very large collections |
| Cross-document reasoning | Strong, since the model sees everything | Limited to what retrieval returns |
| Access control | Hard to apply per user within one large context | Can filter results by user permissions |
| Best fit | Small, stable document sets and deep analysis of a few documents | Large or changing collections with many users |

Long context works well for tasks such as reviewing a single contract in full or comparing a few related documents, where seeing everything at once improves the answer. Retrieval is usually the better choice for high-volume question answering over a large knowledge base. Many systems combine the two: retrieval selects the most relevant documents, and the model then reads those documents in full rather than only short passages.

## Context caching[#](https://www.educative.io/courses/forward-deployed-engineer/model-and-context-trade-offs#Context-caching)

When many requests share the same large block of content, such as a product manual or a fixed system instruction, sending it again with every request repeats the same cost. Context caching stores that shared content so later requests can reuse it at a reduced token rate. Recent Gemini models apply some caching automatically when requests share a common prefix. Explicit caching gives the application direct control over what is cached and for how long.

## Estimating cost per request[#](https://www.educative.io/courses/forward-deployed-engineer/model-and-context-trade-offs#Estimating-cost-per-request)

# Illustrative prices in USD per 1 million tokens. Replace with current published rates.

PRICES = {

"flash": {"input": 0.30, "cached\_input": 0.03, "output": 2.50},

"pro": {"input": 1.25, "cached\_input": 0.125, "output": 10.00},

}

def cost\_per\_request(model, input\_tokens, output\_tokens, cached\_tokens=0):

p = PRICES[model]

fresh\_input = input\_tokens - cached\_tokens

cost = (

fresh\_input \* p["input"]

+ cached\_tokens \* p["cached\_input"]

+ output\_tokens \* p["output"]

) / 1\_000\_000

return cost

# A support request: 8,000-token manual, 500-token question and history, 400-token answer

flash = cost\_per\_request("flash", 8\_500, 400)

flash\_cached = cost\_per\_request("flash", 8\_500, 400, cached\_tokens=8\_000)

pro = cost\_per\_request("pro", 8\_500, 400)

monthly\_requests = 300\_000

for name, cost in [("Flash", flash), ("Flash + cache", flash\_cached), ("Pro", pro)]:

print(f"{name}: ${cost:.5f} per request, ${cost \* monthly\_requests:,.0f} per month")

## Common trade-off mistakes[#](https://www.educative.io/courses/forward-deployed-engineer/model-and-context-trade-offs#Common-trade-off-mistakes)

Several mistakes recur in production designs. The first is using the most capable model for every step without measuring whether a faster model meets the quality bar. The second is placing an entire document collection in the context window for every request because it fits, regardless of cost and latency. The third is caching content that is rarely reused, which adds storage cost without savings. The last is estimating cost from the pilot’s traffic alone, without projecting to production volumes and longer conversation histories.

Model and context decisions determine whether an enterprise AI system stays fast and affordable at scale. Model routing keeps routine traffic on efficient models while reserving stronger models for difficult cases. Retrieval and long context each suit different tasks and often work best together. Caching reduces the cost of shared content, and a simple cost-per-request estimate turns these choices into numbers the customer can plan around. FDEs who tie each decision to quality measurements and a clear cost estimate give customers confidence that the system will remain sustainable after launch.
